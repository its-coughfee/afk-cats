# [HASH] — Planning chat overview: the project's blocking problem was researched to a settled answer, put to Discord twice and published as a public repository, and the chat closed on the user's decision to stop work until Discord can show something over a stream

The chat set out to process nine captures from the first real use of the bot. It
processed two and stopped, because the first item taken turned out to decide
whether the rest are worth doing at all.

**The finding that ran the session.** The user streams a single application rather
than their whole screen, so the sign — a page in a browser tab — is invisible to
viewers for exactly as long as they are working. Their own hypothesis was that a
bot could place something over the stream from inside Discord. It cannot, and the
lookup settled it rather than leaving it arguable: no API exists, it has been
asked for since Go Live shipped and never built, and every surface a bot can
change sits beside the video where a full-screen viewer never sees it. Two
specific limits came out of the same lookup and are worth keeping — a bot can
never rename a server owner, and channel renames are capped at two per ten
minutes, which rules a renamed channel out as a live status. Filed at
`resources/research/discord-cannot-overlay-a-stream.md` with its index line.

**A route was found and then refused, and the refusal is the load-bearing part.**
Switching which window Go Live shares, so the sign is what viewers see while the
user is away, costs nothing and needs no install. The user rejected it: they moved
to single-application sharing deliberately, and a route that reopens the share
picker several times a day puts "share entire screen" under the cursor as a habit.
That is a security judgement about their own behaviour, not a preference, and it
is what reduced the remaining options to installing compositing software or
accepting the sign is not in the stream.

**The escalation, and the warning that preceded it.** The user asked for a GitHub
issue framed as a security issue, claiming the project is terminally blocked, with
this repository linked and made public first. Claude warned once, in a turn of its
own, that three things in that were not true or not survivable — the project was
not blocked at the time, a missing feature filed as a security issue is closed on
the label before the argument is read, and publishing eleven local commits exposes
the whole queue and every log entry permanently. The user's answer removed the
first objection by withdrawing the switch-the-share route, and reaffirmed the
rest. The work then proceeded, which is what a single warning is for.

**What publishing actually took.** A scrub of the working tree and all eleven
commits found no bot token anywhere — the only long hex string is the Discord
application public key, which is public by design — and one real exposure: the
live Worker address in a deploy record carried the user's Cloudflare account
handle, which is the local part of their personal email. On their agreement it was
replaced with a placeholder and the holding commit rewritten, so the string is
absent from history rather than merely removed going forward; the seven log files
citing that commit's hash were updated to the new one. The repository is now
public at github.com/its-coughfee/afk-cats.

**Both attempts at Discord, in order.** The issue was filed and closed within the
hour as misfiled. The argument was then re-posted as a Discussion in the category
the contributor named, on the user's approval of the exact text. Both are recorded
in `INBOX/sent.md`.

**The decision the chat ended on.** The user's words: the project is "terminated
until the issue gets solved". Claude had put a two-way choice to them — pursue the
OBS route, or accept the sign as a page people open — which they had already
closed, and said so. The decision is recorded in
[sign-cannot-show-over-focused-window] along with everything the interview
established, so the next planning run starts from it. How far the hold reaches
across the rest of the queue was asked and never answered, and is carried by
[hold-scope-unanswered]; the readiness line was deliberately left where it stood
rather than moved on an assumption, which is why the advisory says a /next run
started before that question is answered would build four items as though nothing
had been decided.

**Also in this chat:**

A second planning chat was open on this project and had already written a capture
into the queue from its own opening's issue check. It was found, its claim
verified independently, and the user archived it. Nothing was lost.

The user gave sustained correction on verbosity, and it took four attempts to
produce one usable summary of a queue item. The first was written entirely in
back-references — "the issue", "the contributor", "a Discussion" — and the user
quoted it back clause by clause with the question each left unanswered. The second
and third named their subjects but ran four and three paragraphs; only the fourth,

extremely specific rules about what particular turns of the planning and build
commands are allowed to say. This is the method's problem rather than this app's,
so it went as mail to the project the plugin is developed in — as a companion to a
report another of the user's projects had sent the same day on the same subject,
which was found already sitting unread in that inbox.

Nothing in SPEC changed. The sharing sentence it carries is wrong, and correcting

on hold.
